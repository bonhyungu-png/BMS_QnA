# 정밀안전점검·진단(교량편) 지침서 QnA 시스템 설계

## 1. 목표

「시설물의 안전 및 유지관리 실시 세부지침(안전점검·진단 편) 교량편」(2022/2023/2024/2026 4개 판본)을 근거로,

1. 연도별 지침 변경사항을 자동으로 비교·요약
2. 점검자가 입력한 손상 수치(균열폭, 균열률 등)로 부재별 상태등급을 계산
3. 부재별 등급을 취합해 구조형식·본교·전체 시설물 등급까지 산정
4. 판정 근거(표 번호·면수·원문 기준)를 항상 함께 제시

를 제공하는 시스템. 1차 구축 범위는 **안전점검진단_교량편**으로 한정한다(공통편·1.7 보수보강은 범위 외, 3절 참조).

## 2. 데이터 현황 (조사 결과)

- `data/안전점검진단_교량편/` 아래 297개 md 파일, 연도별(2022/2023/2024/2026) 병렬 구조.
- 표는 이미 KV 블록으로 원자화되어 있음: `부재 / 평가항목 / 세부항목 / 등급 / 기준 / 출처`.
- 1.4절 기준 문장(`기준:`) 459개 표본 분석: **정량 36%(167개) / 정성 서술형 49%(223개) / 없음 15%(69개)**.
  - 정성 서술형이 더 많다 — 지침서 본문이 이미 "정량·정성 평가를 동시에 수행하며 최젓값을 기준으로 한다"고 명시하므로, 정성 항목은 시스템이 등급을 확정하지 말고 점검자 판단을 보조하는 형태로 설계한다.
- 등급-블록(342개) 중 27%(94개)가 기준 문장을 2줄 이상 가짐 (예: `균열폭 0.1~0.3㎜` + `균열률 2%미만`) → 서로 다른 측정방식의 **대체 지표(OR)**로 해석. 하나라도 해당 구간에 들면 그 등급.
- `(부재, 평가항목, 세부항목)` 튜플이 연도 간 안정적인 매칭 키. 표 번호는 연도마다 밀림(예: 표1.34 세굴등급판정(2024) → 표1.35~37로 3분할(2026))이므로 연도 비교에 표 번호를 키로 쓰지 않는다.
- 전체 등급 산정에 필요한 가중치표(표1.31/32)·결함도점수표(표1.33)·5단계 산정절차(1.4절 본문)가 모두 교량편 안에 있어 공통편 없이도 계산 가능함을 확인.
- 1.7 보수·보강 절은 원문이 공법 이름 4개뿐(2022~2026 공통, 657바이트 이하) — 손상유형→공법 매핑 근거가 지침서에 없음.

## 3. 범위

**포함**
- 1.1~1.6절 전체 (표+본문), 1.7절은 본문 검색 대상으로는 포함하되 공법 매핑 기능은 만들지 않음
- 부재별 등급 판정(정량 자동 계산 + 정성 후보 제시)
- 5단계 전체 등급 산정(부재→구조형식→본교→전체시설물)
- 연도 간 비교(2022/2023/2024/2026)

**제외 (범위 외, 별도 과제로 남김)**
- 손상유형→보수보강공법 매핑 (지침서에 근거 없음, 국토안전관리원 자료 등 외부 소스 필요)
- 공통편 통합 (현재 데이터 없음)
- 정밀안전진단 특화 로직(정밀안전점검과 겹치는 부분만 우선 지원)

## 4. 아키텍처

```
                        ┌─ grade_lookup()      ─┐
사용자 질문/입력 → LLM(도구선택) ─┼─ aggregate_grade()   ─┼→ 근거+계산결과 → LLM(설명·인용) → 응답
                        ├─ compare_years()     ─┤
                        └─ search_text()       ─┘  (본문 서술형만 RAG)
```

- 표 데이터 = 정규화 DB(SQLite) 질의. 서술형 본문 = 임베딩 검색(RAG).
- 등급 확정·수치 비교는 파이썬이 계산하고 LLM은 호출 결과를 인용해 설명만 한다. LLM이 직접 구간 비교를 하지 않는다.

## 5. 데이터 모델 (SQLite)

```sql
criteria (
  id INTEGER PRIMARY KEY,
  year INTEGER, section TEXT, table_no TEXT, table_title TEXT,
  member TEXT, item TEXT, subitem TEXT,
  grade TEXT,                      -- a~e
  criterion_raw TEXT,              -- 원문 그대로 1개 (다중 기준은 행을 분리)
  criterion_type TEXT,             -- 'quant' | 'qual' | 'none'
  parsed_field TEXT, parsed_min REAL, parsed_max REAL, parsed_unit TEXT,
  page INTEGER, source_path TEXT
)

weight_tables (year, structure_type, member, weight REAL)      -- 표1.31/1.32
defect_score  (year, grade, index_value REAL, range_min REAL, range_max REAL)  -- 표1.33
text_docs     (year, section, heading_path TEXT, paragraph TEXT, source_path TEXT)  -- 1.1~1.7 서술형(표 제외)
```

- `criteria`, `weight_tables`, `defect_score`는 기존 `스크립트/안전점검진단_교량편/구축_1.*.py`가 만든 md의 KV 블록을 파싱해 적재. 신규 파서 스크립트(`구축_DB.py`)에서 정규식으로 `criterion_type`/`parsed_*`를 채운다.
- `text_docs`는 이미 있는 `추출_본문.py` 산출물(`text/*.md`)을 문단 단위로 분해해 적재 + 임베딩 벡터 생성.

## 6. 판정 로직

### 6.1 정량 파서
- 대상 패턴: `X㎜미만`, `X이상～Y미만`, `X%이상`, `X이상` 등. 정규식으로 `(field, min, max, unit)` 추출.
- 파싱 실패(사람이 봐도 애매한 표현 포함)는 `criterion_type='qual'`로 폴백 — 침묵 실패 대신 명시적으로 "정성 판단 필요"로 표시.

### 6.2 grade_lookup
- `criterion_type='quant'`인 레코드들을 대상으로 입력 측정값이 속하는 구간 탐색.
- 여러 정량 지표(OR 관계) 중 하나라도 해당 구간에 들면 그 등급 채택. 여러 지표가 서로 다른 등급을 가리키면 **더 나쁜(낮은) 등급** 채택 — 이는 1.4절 본문의 "최젓값 기준" 원칙과 동일 해석.
- `criterion_type='qual'`뿐이면 등급을 확정하지 않고 해당 부재·항목의 등급별 원문 서술 전체를 반환, LLM이 "가장 가까운 서술과 그 등급, 근거 출처"를 제시하되 최종 판단은 점검자 몫임을 답변에 명시.

### 6.3 aggregate_grade (5단계)
1.4절 본문 산정 절차를 그대로 코드화:
1. 부재별 상태평가 → 2. 가중치 적용 환산 결함도 점수(표1.31/32) → 3. 결함도 점수 범위(표1.33)로 구조형식별 등급 → 4. 연장비 가중합으로 본교 등급 → 5. 본교/램프교/접속교 연장비 가중합으로 전체 등급.
중대결함 발생 시 해당 부재/구조형식 최젓값을 우선 적용하는 예외 규칙 포함(1.4절 본문에 명시된 규칙).

### 6.4 compare_years
`(member, item, subitem)` 키로 연도별 `criterion_raw`/`grade` 목록을 나란히 조회 → 신설/삭제/구간 변경/표 번호 이동을 diff로 반환.

## 7. 백엔드 (FastAPI)

```
POST /chat            {message, session_id} → 도구 호출 오케스트레이션 후 답변+출처
POST /inspection/grade {member, item, subitem, measures, year} → grade_lookup 결과
POST /inspection/aggregate {member_grades, structure_type, span_ratios, critical_defect?} → aggregate_grade 결과
GET  /compare          ?member=&item=&subitem=&years= → compare_years 결과
GET  /search           ?q=&section=&year= → search_text 결과
```

- 세션 상태(점검표에 입력된 부재별 등급)는 서버 메모리/세션 스토어에 유지해 채팅에서도 참조 가능하게 한다.
- 기존 `QA/qna.py`의 provider/모델 설정 로직(anthropic/nvidia/openai 자동판별)은 재사용.

## 8. 프론트엔드 (React)

- **채팅 탭**: 자유 질문 → 답변 + 출처 칩(표 번호/면수) 표시.
- **점검표 탭**: 부재 목록(1.2절 현장조사 표 기준) 나열 → 부재별 손상 수치 입력 폼 → 실시간 `grade_lookup` 호출로 등급 표시 → "전체 등급 계산" 버튼으로 `aggregate_grade` 실행, 계산 과정(가중치·결함도점수) 트리 형태로 표시.
- 두 탭은 세션 상태를 공유(점검표 입력값이 채팅 문맥에도 노출).

## 9. 테스트 계획

- 파서 단위테스트: 정량 기준 문장 샘플(quant 167개) 전수 파싱 검증, 실패율 리포트.
- grade_lookup 골든셋: 표1.11~1.29 각 부재별 대표 입력값 → 기대 등급 수기 검증.
- aggregate_grade 골든셋: 1.4절 본문 예시(강거더교 등 계산 예시 있으면 활용) 재현.
- compare_years: 2024→2026 표1.34→1.35/36/37 분할 케이스로 회귀 테스트.

## 10. 마이그레이션 순서 (참고, 상세 계획은 이후 구현계획 문서에서)

1. 정규화 파서(`구축_DB.py`) 작성 → SQLite 적재 → 정량 파싱 커버리지 확인
2. 도구 함수(grade_lookup/aggregate_grade/compare_years/search_text) 구현 + 단위테스트
3. FastAPI 엔드포인트 + LLM 오케스트레이션(도구 호출) 연결
4. React 채팅 탭 → 점검표 탭 순으로 프론트 구현
5. 골든셋 기반 통합 테스트
